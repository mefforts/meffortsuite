# Enchant Queue 1.1.7 review

The reported problem was discoverability: Next existed only inside the separate configuration panel. It did not appear by Blizzard's Enchant button. The feature now creates visible Queue and Next enchant controls when the Enchanting window is open and the feature is enabled, before configuration is ever opened.

Queue shows the remaining count and opens recipe/target/count configuration. Next remains available with configuration closed, and the existing keybinding retains its global button name. Closing configuration alone keeps owned cast tracking; closing Enchanting, disabling the feature/master or entering combat withdraws the controls. Each enchant and replacement confirmation still requires a separate input. Recipe, target GUID, allocation and quantity verification, matching cast ownership and uncertain-result handling remain in place.

Both controls are owned by UIParent. Placement reads the native CreateButton center, dimensions and scale, then writes only private geometry. The preferred position is beside Enchant; a compact row above is used when the right edge lacks room. Native frames are neither moved nor made ancestors of the secure button. Placement writes are deduplicated, and a limited visible-window ticker follows native movement/scale and recovers late button geometry. It stops when the feature/window is inactive or combat begins. Native profession-data events coalesce deferred synchronization and recover metadata that was not ready on first show.

The restricted combat handler hides and disarms Next. Ordinary callbacks avoid protected writes during combat; the configuration panel and Queue launcher are private ordinary frames. The actual native recipe control must be visible before Next can stage a craft, so the keybinding cannot submit from a hidden crafting tab. No timer casts or confirms an enchant. Unavailable secure state handling keeps Next blocked with native-control guidance.

When configuration is closed, failed preparation gives a chat explanation with short duplicate suppression. Next has status help, /msuite enchant status reports queue/control/layout/phase state, and diagnostic exports include that state. Status commands do not toggle configuration.

Native source was checked for the Professions CraftingPage.CreateButton, GetRecipeInfo/GetTransaction, Item-based enchant allocation and the separate native click path. The layout uses the actual button rather than hard-coded profession-window offsets. The tests simulate these contracts; they do not establish live native protected-click acceptance or rendering.

All 32 regression scripts pass: 401 unit-test methods plus five tooltip script checks. Enchant Queue now has 39 cases, including first-show visibility, complete UI configuration/drag/add/close/Next flow, in-flight tracking with configuration closed, movement/scale/narrow placement, unchanged-placement deduplication, lifecycle cleanup, guarded combat withdrawal, hidden recipe controls, late metadata/button recovery and chat/status feedback. Existing replacement, staging, allocation, quantity, manual-cast, uncertain-result and persistence cases remain covered. Diagnostic command/report inclusion has a separate regression.

In Forever, verify Queue/Next beside Enchant on first open, configure two inexpensive enchants, use Next with configuration open/closed, confirm replacement with a separate input and check the count. Repeat with the existing keybinding, window movement/minimizing, several UI scales, a narrow viewport, feature/master changes, combat and native window closure. If blocked, run /msuite enchant status or export before reload. Use the native Enchant control if this client's protected input is unsupported.
